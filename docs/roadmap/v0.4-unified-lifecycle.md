# v0.4 implementation plan: Unified lifecycle

## Objective

Make the `lake` CLI the single user-facing entry point for configuring and
operating the local platform.

## Public command target

```text
lake platform init
lake platform up
lake platform down
lake platform status
lake platform doctor
lake platform logs
```

## Scope

### Initialization

- Interactively or non-interactively select a data root and container backend.
- Create private configuration and required directories idempotently.
- Generate local credentials and bootstrap the Polaris realm and catalog.
- Refuse to overwrite existing credentials or re-bootstrap initialized state.

### Runtime operations

- Start and stop services in dependency order.
- Display service health and local endpoints without exposing credentials.
- Provide bounded log access with service selection.
- Separate normal startup from one-time bootstrap operations.

### Doctor checks

- Check supported Python and DuckDB versions, container capabilities, ports,
  directory permissions, free space, configuration, and service health.
- Classify results as pass, warning, or failure with actionable remediation.
- Keep doctor read-only unless an explicit repair command is introduced later.

## Work sequence

1. Create a process-runner abstraction using argument arrays, not shell
   command strings.
2. Implement structured diagnostics and JSON output.
3. Implement idempotent initialization and credential generation.
4. Implement service lifecycle around the existing Compose definition.
5. Convert old scripts into thin deprecation wrappers.
6. Add failure-path and interrupted-bootstrap tests.

## Acceptance criteria

- A fresh supported Linux or WSL checkout can be initialized and started using
  only documented `lake platform` commands.
- Re-running `init` does not rotate credentials or destroy state.
- `doctor` detects occupied ports, missing container support, and unwritable
  storage before bootstrap.
- Failed bootstrap steps leave actionable diagnostics and can be safely
  retried.
- All commands provide machine-readable JSON output.

## Non-goals

- Remote cluster deployment or orchestration.
- Automatic destructive repair.
- Scheduling data pipelines.
