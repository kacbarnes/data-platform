# v0.6 implementation plan: Installation portability

## Objective

Install and use the platform client through standard Python tooling without
requiring a particular Conda distribution or an external DuckDB executable.

## Scope

### Python packaging

- Declare complete runtime and optional development dependencies in
  `pyproject.toml`.
- Support virtual environments, `pip`, `pipx`, `uv`, and Conda/Mamba.
- Define and test supported Python versions rather than encoding one local
  interpreter path.
- Add lock or constraints guidance for reproducible installations.

### Query experience

- Implement `lake query --sql`, `--file`, and an interactive mode using the
  Python DuckDB package.
- Keep the external DuckDB CLI as an optional enhanced client.
- Ensure both query paths use the same catalog attachment and credential
  configuration.

### Release artifacts

- Build source distributions and wheels in CI.
- Verify installation into a clean environment without repository imports.
- Evaluate standalone Python executables only after normal packaging works.

## Work sequence

1. Audit imported modules against declared dependencies.
2. Replace fixed interpreter and DuckDB executable assumptions.
3. Implement Python-native query modes.
4. Add clean-wheel installation tests.
5. Document each supported installer with equivalent verification commands.

## Acceptance criteria

- A clean `venv` installation can run datasets, status, doctor, ingest, test,
  and query commands.
- `pipx`, `uv tool`, and Conda/Mamba installation paths pass smoke tests.
- The core workflow does not require a separately installed DuckDB CLI.
- Wheels contain contracts/templates only when intentionally packaged and do
  not contain machine state or credentials.
- Unsupported Python or DuckDB versions produce actionable errors.

## Non-goals

- Replacing Python with Rust or C.
- Embedding the container images in the Python package.
- Publishing to a public package index without a release decision.
